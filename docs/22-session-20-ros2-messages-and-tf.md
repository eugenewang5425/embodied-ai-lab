# 第二十课：先看小车怎样走，再看定位程序怎样合作

本课沿用第十九课的小车、测量和定位算法，只把工作交给三个独立运行的 ROS 2 进程。先学会数据怎样交接，再考虑更复杂的机器人。ROS 不会因为接入了消息系统，就自动提高定位精度。

## 先把实验目的说清楚

项目最终要形成“测量 → 定位 → 规划 → 控制运动”的闭环。本课只接通测量与定位，没有实现后两步。

**小车实际怎样运动？** 当前方形案例按预设轮速，直行 0.8 m、原地左转 90°，重复四次，共 24 s。蓝色车体显示冻结记录中的运动学真值；这是理想无打滑的二维仿真，不是实车录像，也不是新加入了电机力矩仿真。图中车体是示意轮廓，两个轮子的间距沿用 0.30 m。

**定位为什么有用？** 轮子读数有噪声，只靠它累计出来的位置会偏。三个已知地标提供外部位置基准，让定位程序重新判断“我在哪”；不是让车瞬间跳到另一个地方。蓝色真值只用于显示和评价，定位节点读不到它。

**第二十课具体增加了什么？** 之前读取测量、计算位置在同一程序里；现在通过 ROS 由独立程序合作。成功标准是每一帧的信息接得上、重算位置与原方法一致。它是将来接入不同传感器和控制程序的系统基础，不是一个更准的定位算法。

**为什么车没有因为校正而改变路线？** 目前轮速仍按预设时间表执行，位置估计没有反馈到轮子。自主回家或追踪目标需要下一段规划／控制闭环，不能把本课的方形运动当成自动导航成功。

## 1. 为什么现在学习 ROS？

之前，一段 Python 程序可以直接把数组传给另一个函数。机器人系统中，读取编码器、处理传感器、估计位置往往由不同程序负责，需要约定：传什么、什么时候测的、在哪个坐标系下表达。

可以类比 GIS 中不同程序交换空间数据：不仅要有数值，还要知道字段含义、采集时间和坐标参考。这里使用局部平面刚体变换，不是经纬度投影。

```text
传感器回放节点 ──编码器／地标──→ 定位节点 ──位姿／TF──→ 核验节点
       └──────────────原始测量副本───────────────→ 核验节点
```

- 传感器节点只加载冻结测量，不发布真实位置。
- 定位节点没有结果文件路径，只订阅测量，重新执行旧算法。
- 核验节点才读取旧结果，与实际收到的位姿和 TF 逐帧比较。

节点是工作单元；话题（topic）是命名的数据通道；消息类型约定字段。一个话题可以有多个订阅者。本课选择一节点一进程，并非 ROS 要求所有节点必须如此。

## 2. 消息里究竟有什么？

| 话题 | 消息类型 | 主要内容 | frame_id |
| --- | --- | --- | --- |
| `/lesson20/encoders` | `sensor_msgs/JointState` | 左右轮累计转角，rad；右轮已做固定比例标定 | `base_link` |
| `/lesson20/landmark_points` | `sensor_msgs/PointCloud2` | 三个已知地标的传感器局部 x/y/z 和编号 | `sensor` |
| `/lesson20/odom_pose` | `geometry_msgs/PoseStamped` | 纯编码器累计的车体位姿 | `odom` |
| `/lesson20/fused_pose` | `geometry_msgs/PoseStamped` | 观测重置＋里程计的车体位姿 | `map` |

`JointState` 用关节名区分左右轮；转角是关节量，不是地图中的 x/y。位姿消息用 x/y 和绕 z 轴的四元数表达二维位置与朝向。

地标的原始来源仍是旧实验的带噪声距离 `r` 和方位角 `β`，发送前转换为 `x=r cos β, y=r sin β, z=0`，接收后按地标编号还原测距测角，调用原来的二维刚体配准。这个 PointCloud2 **只有三个合成控制点**，没有新增相机、激光扫描或识别算法。

### 时间戳为什么不能省？

编码器每个仿真步都有一条，步长 0.04 s；地标每 2 s 一条。在第 50 帧，两类读数属于同一时刻。跨话题到达顺序不可靠地代表测量时间，因此定位节点按整数时间戳配对，两者到齐才输出这帧的校正结果，不能把旧地标直接当成当前观测。

消息时间戳统一为 `1 s + 帧号 × 0.04 s`，并发布 `/clock`。加 1 s 是为了避免 tf2 把零时刻当作“查询最新变换”；教学时间仍从 0 s 开始。这是同一仿真时钟，不是真实设备的时钟同步。

当前已知地标采样日程。缺少对应观测就等待，超时明确失败；没有丢包降级、迟到观测回溯或网络时延补偿。缓存有上限，拒绝重复、过旧、非有限值和远超窗口的测量。

## 3. TF 为什么分成四个坐标系？

```text
map ──全局校正──→ odom ──连续里程计运动──→ base_link ──固定安装──→ sensor
```

把 `T_A_B` 理解为“B 坐标系在 A 中的位姿”，也可用它把 B 中的点转换到 A。

- `odom → base_link`：编码器一直累计，不因地标校正而重置，保留局部运动连续性。
- `map → odom`：承载地标带来的全局修正，观测时允许跳变。
- `base_link → sensor`：前方 0.12 m、左侧 0.04 m、旋转 +30° 的固定安装关系。

原融合算法算出的位姿是 `T_map_base`，于是：

```text
T_map_odom = T_map_base × inverse(T_odom_base)
T_map_sensor = T_map_odom × T_odom_base × T_base_sensor
```

第二行是 tf2 沿坐标树完成的查询，不再额外广播一条 `map → sensor` 边。前两条动态边通过 `/tf` 广播，固定安装通过 `/tf_static` 广播。新订阅者也能收到此前发布的静态变换，本次已实际验证。

TF 负责组织和查询变换，不会自动校正错误安装参数或地图。本课仍是观测直接重置，没有卡尔曼滤波。定位数字没有变，改变的是它们在系统中的组织方式。

## 4. 先看这几个变化

在项目目录的 PowerShell 中运行只读教学回放：

```powershell
uv run python -m embodied_learning.ros2_system_demo
```

默认读取 `results/ros2_system_2026-09-03_v2`，暂停、0.25×。这是**真实 ROS 收发记录的回放**，窗口不启动 ROS，也不是正在连接机器人。

新版默认打开“① 先看小车与定位”，消息和 TF 分别在第二、三页，不要求先读表格。

1. 点“播放”：看左侧蓝色小车沿预设路线行驶。蓝色车体是真值；紫色空圈是纯里程计，橙色空圈是地标融合，后两者只是同一辆车的估计位置。
2. 点“看转弯”：暂停在第一段原地左转的首帧 4.04 s。继续播放或单步，观察车头转向，但车体中心不平移；不是到路口就瞬间换方向。
3. 回到“起点”，点“下一次观测”：到 2.00 s。绿线只示意本帧观测的三个地标，不是画出真实激光或原始测距射线。
4. 点“同帧：看校正前／后”：**时间固定在 2.00 s，蓝色车体固定不动**，只切换橙色估计。右侧灰圈与箭头表示校正前的预测到校正后结果；下方说明这次误差变小还是变大，不把有噪观测包装成必然改善。
5. 右侧是厘米尺度的误差放大镜，始终让蓝色真值居中，坐标轴与地图同向。与蓝点的偏移来自原始数据，没有放大或改写误差值；轴范围整段固定，不能把镜头居中理解成实际车辆停着。箭头表示朝向，圆圈不是车体尺寸。

校正前预测由“前帧融合位姿 × 本帧相对里程计增量”还原，不使用真值或未来观测。切换前／后只改变画面，第二页的消息仍是实际收到的结果，不伪造一个额外 ROS 运行。

看懂运动以后再去第二页：第 49 帧地标 0 条，第 50 帧变成 1 条，时间戳 3.00 s。第三页查看 `map → odom` 的校正和固定安装关系。实验文件、消息记录和计算算法均未因改版而变化。

## 5. 重新运行真实 ROS 实验

已核验 WSL2 `Ubuntu-24.04`、ROS 2 Jazzy、Linux Python 3.12.3、NumPy 1.26.4；Windows 项目仍使用自己的 uv 虚拟环境。没有搬用 Windows 虚拟环境，也没有为本课安装第二套 MuJoCo。

PowerShell 一条命令会导出测量、启动三个 Linux 进程、逐帧验收并清理本次子进程：

```powershell
uv run python -m embodied_learning.experiments.ros2_system --route square --output results/ros2_system_my_run
```

必须使用新输出目录，不覆盖既有数据。可选 `--route straight` 或 `--route long`；`--run-index 0` 选择旧记录的噪声样本。反转发布顺序：

```powershell
uv run python -m embodied_learning.experiments.ros2_system --route square --observations-first --output results/ros2_system_my_reversed_run
```

该选项只控制发布先后，不能保证 DDS 跨话题接收顺序；纯逻辑测试另行强制两种实际输入顺序。

本课用已有 `rclpy` 运行 Python 模块作为节点，尚未制作 ament/colcon 包、launch 文件或 RViz 配置。限定 `ROS_DOMAIN_ID=87`、`ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST`，只在本机通信；同一域下请逐个运行实验。

为避免第一帧早于订阅连接，增加 `/lesson20/ready` 就绪握手；核验节点调用 `/lesson20/step` 发一帧，等待验收完成，再要下一帧。话题使用可靠 QoS。这是教学用单步确认，不是实时吞吐或延迟测试。

若要检查活着的节点，可在新目录运行时增加 `--hold-seconds 60`，再在另一个终端执行 `wsl -d Ubuntu-24.04`，进入 Linux 后：

```bash
source /opt/ros/jazzy/setup.bash
export ROS_DOMAIN_ID=87
export ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST
ros2 node list --no-daemon
ros2 topic list --no-daemon
ros2 interface show geometry_msgs/msg/PoseStamped
```

保留阶段数据已发完，节点暂时还活着；不要把此时收不到新位姿消息误判为故障。保留期结束自动退出，不留下本课的常驻进程。

## 7. 这一课学会三句话就够了

1. 节点把工作拆开，话题和消息把数据接起来。
2. 数字要带采样时间和坐标语义，才能被正确使用。
3. TF 组织坐标变换；定位算法提供变换数值，两者不是同一件事。

停止边界：没有新增自由度、物理引擎、运动纠偏、导航、SLAM、硬件接口或滤波算法。理解本课以后，一个更直观的后续候选是“用估计位置驱动小车到目标点”，以实际到达误差检验定位的用途；本次没有实现。ROS 包和启动配置应服务于具体任务，不单独作为不断堆叠的进度。
